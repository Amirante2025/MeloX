# 收藏歌曲加载与播放响应优化

本次实现收藏缓存、收藏优先加载和渐进式“播放全部”。不加入心动模式推荐预热，心动模式继续在点击后请求推荐。

## 可见行为

- 成功同步过一次后，重启先恢复当前登录会话的收藏首屏，后台更新。离线或刷新失败时保留缓存列表。
- 账号校验、歌单和收藏首批资料优先完成；个人详细资料、专辑、歌手、播客和历史随后并行加载。
- “播放全部”立即以已加载的收藏启动播放，剩余歌曲资料每批 100 首后台追加，保持收藏顺序，不重启当前歌曲。
- 到达已加载队列的末尾时等待下一批，避免提前结束或只循环首批歌曲。补充失败时，队列提供重试入口，保留失败批次。
- 另选歌曲或切换播放集合会使旧补充任务失效；等待中的“下一首”也不能误操作新的集合。随机顺序和当前播放位置由现有队列管理。

## 缓存边界

缓存包含账号基本资料、收藏歌单 ID、完整有序歌曲 ID 和首批最多 100 首的资料。首屏的解码量固定，音频文件仍由现有下载系统管理。首次安装后仍需联网完成初次同步。

缓存位于系统 Caches 目录，文件名使用登录 Cookie 的 SHA-256 摘要，文件内容不保存 Cookie。不同登录会话分开存储，退出登录清理当前缓存；损坏缓存直接回退到联网加载。文件写入使用串行后台队列和原子替换。

播放队列后续补齐的是歌曲资料；网络音源获取、音频格式检测和缓冲依然取决于网络。没有增加心动推荐缓存或预取，也没有修改推荐接口的请求方式。

## 验证

在 macOS 安装 Apple Command Line Tools 后，从仓库根目录运行：

```sh
python3 Tools/Checks/check_library_performance.py
python3 Tools/Checks/check_progressive_playback.py
```

第一组直接编译实际 LibraryStore、缓存、歌曲模型与队列补充器，以受控 API 验证缓存恢复、离线保留、账号隔离、首屏优先、并行补充请求、排序、取消和失败重试。

第二组从实际 PlayerStore 提取加载、播放、切歌和补队列入口，连同实际 PlaybackQueue / PlaybackTimelineClock / PlaybackQueueExpansion 编译，以受控音源和引擎验证先播放后补齐、队列隔离、队尾等待，并回归切歌归零和显式续播进度。

这两组检查验证逻辑，不替代 iPhone 上的界面与网络耗时检查。云端继续使用现有 iPhone Release IPA 构建流程，不生成模拟器截图。
