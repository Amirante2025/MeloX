# 收藏歌曲加载与播放响应优化

本次实现收藏缓存、收藏优先加载和渐进式“播放全部”。不加入心动模式推荐预热，心动模式继续在点击后请求推荐。

## 可见行为

- 成功同步过一次后，重启先恢复当前登录会话的收藏首屏，后台更新。离线或刷新失败时保留缓存列表。
- 账号校验、歌单和收藏首批资料优先完成；个人详细资料、专辑、歌手、播客和历史随后并行加载。
- “播放全部”立即以已加载的收藏启动播放，剩余歌曲资料每批 100 首后台补齐，不重启当前歌曲。
- 收藏队列在加载资料前预留完整歌曲 ID 顺序。关闭随机时保留收藏顺序；开启随机时对完整集合生成一次随机顺序，后台按该顺序获取缺失资料，不再分别打乱各个 100 首批次。已缓存歌曲也不能越过尚未加载的前置歌曲。
- 首曲仍沿用原有行为，从收藏的第一首可用歌曲开始；本次没有加入随机选择首曲。直接点选歌曲的行为也不变。
- 到达尚未加载的歌曲位置时等待资料，避免跳过该曲、提前结束或只循环首批歌曲。补充失败时，队列提供重试入口，保留失败批次；成功响应中缺失的不可用歌曲会移出预留顺序，避免形成永久阻塞。
- 切换随机状态会同步调整剩余资料的请求优先级，当前歌曲和进度保持不变。另选歌曲或切换播放集合会使旧补充任务失效；等待中的“下一首”也不能误操作新的集合。

下载页“下载管理”选项将原先文字区域单独增加的 12 点底部留白，改为整行上下各 6 点的对称留白，保留总留白高度并使文字、容量与系统右侧箭头居中对齐。

## 缓存边界

缓存包含账号基本资料、收藏歌单 ID、完整有序歌曲 ID 和首批最多 100 首的资料。首屏的解码量固定，音频文件仍由现有下载系统管理。首次安装后仍需联网完成初次同步。

缓存位于系统 Caches 目录，文件名使用登录 Cookie 的 SHA-256 摘要，文件内容不保存 Cookie。不同登录会话分开存储，退出登录清理当前缓存；损坏缓存直接回退到联网加载。文件写入使用串行后台队列和原子替换。

播放队列后续补齐的是歌曲资料；网络音源获取、音频格式检测和缓冲依然取决于网络。没有增加心动推荐缓存或预取，也没有修改推荐接口的请求方式。

## 验证

在 macOS 安装 Apple Command Line Tools 后，从仓库根目录运行：

```sh
python3 Tools/Checks/check_library_performance.py
python3 Tools/Checks/check_progressive_playback.py
```

第一组直接编译实际 LibraryStore、缓存、歌曲模型与队列补充器，以受控 API 验证缓存恢复、离线保留、账号隔离、首屏优先、并行补充请求、排序、取消和失败重试。

第二组从实际 PlayerStore 提取加载、播放、切歌和补队列入口，连同实际 PlaybackQueue / PlaybackTimelineClock / PlaybackQueueExpansion 编译，以受控音源和引擎验证先播放后补齐、队列隔离、队尾等待，并回归切歌归零和显式续播进度。新增检查验证完整 350 首随机计划与 350 次实际播放选择一致、缓存不能越过未解析的位置、跨批次不重新洗牌、加载中切换模式的取消与重排、不可用歌曲处理，以及手动队列编辑兼容。比较的是同一次生成的完整计划与实际结果，不依赖某首随机歌曲恰好落在某个位置。

这两组检查验证逻辑，不替代 iPhone 上的界面与网络耗时检查。云端继续使用现有 iPhone Release IPA 构建流程，不生成模拟器截图。
